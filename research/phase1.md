# Phase 1: Symbolic Regression for Incremental Softmax Approximation

## Problem

The incremental (online) softmax update is the inner loop of attention in transformer models. Given a running max `m` and running sum `s`, incorporating a new logit `x` requires:

```
m_new = max(m, x)
s_new = s * exp(m - m_new) + exp(x - m_new)
```

This costs two `exp()` calls when `x > m`, one otherwise. The goal was to find algebraic approximations for `s_new(m, s, x)` that are cheaper to evaluate on GPU while remaining accurate enough to not degrade model quality.

---

## Approach

### Data Generation

Synthetic sequences were generated by simulating the incremental softmax over streams of `randn()` logits. Each sample is `(m, s, x) → s_new`. 100,000 samples were generated per training round, with 15% refreshed each iteration to prevent overfitting to a fixed distribution.

### Symbolic Regression

PySR (via `SymbolicRegression.jl`) was used to search for compact symbolic expressions approximating `s_new`. The search space:

- Binary operators: `+`, `-`, `*`, `>` (greater-than, returns 0/1)
- Unary operators: `abs`
- Max complexity: 40 nodes
- Loss: MAE with a small tree-depth penalty (removed in later variant)

Runs were checkpointed every 30 iterations, with hall-of-fame CSVs saved throughout.

### GPU Benchmarking Infrastructure

Three scripts were built to close the loop between SR discovery and GPU performance:

**`cuda_bench.py`** — generates a `.cu` file per equation. Each kernel:
- One thread per attention sequence (batch × heads parallelism)
- Transposed input layout `logits[step * N_SEQS + seq]` for coalesced warp reads
- `__ldg()` for read-only cache, `#pragma unroll 4` on the inner loop
- Timed with CUDA events; reports G-updates/s and µs/seq

**`eval_bench.py`** — end-to-end pipeline:
- Deduplicates equations by string across all run directories (first occurrence wins)
- Generates `.cu` files in parallel (4+ workers)
- Compiles with `nvcc` in parallel (4+ workers), caching by `.cu` mtime vs binary mtime
- Runs binaries sequentially (one GPU), appending results to `bench_results.csv` incrementally

**`analyze_bench.py`** — feature extraction and correlation analysis:
- Filters to equations within a loss threshold of the minimum
- Parses each equation into a full AST
- Extracts 124+ structural features (tree shape, variable depths, CSE opportunities, polynomial degree, constant statistics, correction subtree structure, etc.)
- Correlates features with GPU throughput

## Results

| Metric | Value |
|--------|-------|
| Unique equations benchmarked | 8,256 |
| Minimum MAE achieved | 0.000949 |
| Equations within 30% of min loss | 240 |
| Baseline throughput (2× `__expf`) | 24.34 G-ups/s |
| Best SR throughput (within 30%) | 24.53 G-ups/s |
| Throughput range (top accuracy tier) | 23.4 – 24.5 G-ups/s |

The SR approximations cluster tightly around the baseline in throughput. The best accurate equation slightly outperforms the baseline (~+0.8%) but no approximation achieves a dramatic speedup. This makes sense: with `--use_fast_math`, `__expf` is already highly optimised on NVIDIA hardware, and the SR approximations that achieve competitive accuracy tend to be algebraically complex enough to cost similar arithmetic.

---

## Feature Analysis

At the 30% loss threshold (240 equations), the top correlators with throughput:

| Feature | r | Direction |
|---------|---|-----------|
| `n_constants` | −0.62 | More fitted constants → slower |
| `x_min_depth` | −0.59 | x buried deep in tree → slower |
| `frac_const_leaves` | −0.56 | Constant-heavy leaves → slower |
| `frac_var_leaves` | +0.56 | Variable-heavy leaves → faster |
| `all_var_depth_mean` | −0.53 | Deep variables on average → slower |
| `all_var_depth_std` | −0.47 | Uneven variable depths → slower |
| `n_mx_products` | −0.48 | m×x interactions → slower |
| `n_distinct_ops` | −0.44 | Mixed op types → slower |
| `x_poly_degree` | +0.40 | Higher x polynomial degree → faster |
| `n_const_mul` | +0.37 | Const×const (foldable) → faster |

Key takeaways:

- **Variable depth is the strongest structural predictor.** Deep `x` occurrences create long serial dependency chains that the GPU cannot pipeline away. Equations where variables appear shallower in the tree are systematically faster.
- **Constant saturation hurts.** Equations with many tuned floating-point constants have a high leaf-to-operator ratio, indicating finely-fitted polynomial approximations. These have high complexity without proportional speed benefit.
- **x² patterns are a positive signal.** Expressions involving `x * x` (quadratic approximations) tend to be faster — they replace `exp()` with multiplication while still capturing the curvature of the exponential locally.
- **Op variety slows things down.** Mixing `+`, `*`, `abs`, and `greater` in one expression prevents the compiler from scheduling uniform FMA chains.

---

## Speed-Aware SR Loss (`run_sr_tree_loss.jl`)

A modified SR runner was written incorporating the above as a small structural penalty added to MAE:

```
loss = MAE + SPEED_WEIGHT × speed_score
SPEED_WEIGHT = 2e-4
```

The speed score (∈ [0, 1]) penalises:
- Average depth of `x` occurrences (w=0.28)
- Std of all variable depths (w=0.20)
- Fraction of constant leaves (w=0.30)
- Number of distinct operator types (w=0.14)

And rewards:
- `x²` polynomial patterns (w=−0.08)

At typical accuracy-frontier MAE (~0.003), the maximum penalty is ~0.0002, or ~7% of MAE. The intent is to break ties between equally accurate equations toward structurally faster forms, without steering evolution away from good solutions early in the search.

The old flat depth penalty (`NESTING_PENALTY = 1e-4 × depth`) was removed in favour of this richer, data-driven formulation.

---

## Limitations and Open Questions

1. **Throughput ceiling.** The baseline with `--use_fast_math` is already near-optimal for this kernel shape. Pure arithmetic approximations may never beat it without changing the access pattern or kernel structure.

2. **Accuracy vs. speed tradeoff is narrow.** Within the 30% accuracy band, throughput variance is only ~4% (23.4–24.5 G-ups/s). SR is finding algebraically different but computationally similar expressions.

3. **Single-thread-per-sequence kernel.** Our benchmark has N_SEQS = 1024 threads, which under-utilises a modern GPU. A warp-reduction kernel (like blog kernel 3/4) might shift which equation structures are fastest.

4. **Approximation fidelity in context.** MAE on the running sum `s_new` doesn't directly translate to attention output error. The error accumulates across the full sequence length and its effect on model outputs is unknown.
