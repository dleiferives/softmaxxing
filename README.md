# softmaxxing

Symbolic regression search for algebraic approximations to the incremental online softmax update — the inner loop of attention in transformer models.

## The Problem

At each step of online attention, incorporating a new logit `x` into a running max `m` and running sum `s` requires:

```
m_new = max(m, x)
s_new = s * exp(m - m_new) + exp(x - m_new)
```

When `x > m`, this costs two `exp()` calls. Otherwise one. The goal: find compact symbolic expressions for `s_new(m, s, x)` that are algebraically cheaper while remaining accurate enough that the error doesn't compound badly across a full sequence.

## Approach

[PySR](https://github.com/MilesCranmer/PySR) (`SymbolicRegression.jl`) does the search over expression trees with `+`, `-`, `*`, `>`, and `abs` as primitives. Training data is 100k synthetic samples generated by simulating the incremental softmax over `randn()` logit streams, with 15% refreshed each iteration to prevent the search from overfitting to a fixed distribution. Loss is MAE with an optional structural penalty (more below).

Runs checkpoint hall-of-fame CSVs every 30 iterations. The benchmarking pipeline deduplicates equations across all run directories, compiles them in parallel, and appends throughput results incrementally.

## What Was Built

**`run_sr.jl`** — the SR runner. Configures PySR, manages the outer training loop, and saves Pareto-frontier CSVs.

**`run_sr_tree_loss.jl`** — modified runner with a data-driven structural penalty added to MAE. More on this below.

**`csv_bench.py`** — generates C++ microbenchmarks from a hall-of-fame CSV. Each equation compiles to a standalone binary (`-O3 -march=native`) that times the update over 100k × N_ROWS calls with a warm-up pass.

**`cuda_bench.py`** — generates CUDA kernels from a hall-of-fame CSV. Each kernel runs a realistic attention configuration (batch=32, heads=32, seq_len=2048 by default), one thread per sequence, with transposed logit layout for coalesced warp reads, `__ldg()` for read-only cache hits, and `#pragma unroll 4` on the inner loop. Timed with CUDA events.

**`eval_bench.py`** — end-to-end pipeline: deduplicates across run directories, generates and compiles `.cu` files in parallel (4+ workers with mtime-based caching), runs sequentially on the GPU, appends results to `bench_results.csv`.

**`analyze_bench.py`** — filters to high-accuracy equations, parses each into a full AST, extracts 124+ structural features (tree shape, variable depths, CSE opportunities, polynomial degree, constant statistics), and correlates them with GPU throughput.

**`eval_cpu_bench.py`** — CPU counterpart to `eval_bench.py`. Reads equations from any CSV, generates C++ microbenchmarks, compiles with `-O3 -march=native`, times them, and appends results to `cpu_bench_results.csv` (separate from the GPU results).

**`analyze_cpu_bench.py`** — joins CPU timing against the pre-computed structural features and correlates them with `ns_per_call`. Saves to `cpu_equation_features.csv`.

**The SR approximations are 3–5× faster than the baseline on CPU.** The best accurate equations come in at ~4.6 ns/call vs 24.4 ns for the exact update. Every single equation in the accuracy tier beats the baseline, with the spread (4.6–7.1 ns) driven by structural differences in the expression tree.

This is the opposite of the GPU story. On CPU, `std::exp` dominates: it takes roughly 20+ ns in the scalar path and the compiler cannot amortize it across threads. The SR expressions avoid `exp` entirely — they're built from `+`, `-`, `*`, `abs`, and `greater`, all of which are single-cycle or close to it. The result is that even the slowest accurate approximation is 3.4× faster than the exact update.

### Structural Predictors of CPU Speed

| Feature | r | Direction |
|---------|---|-----------|
| `tree_n_nodes` | +0.78 | Larger tree → slower |
| `complexity` | +0.78 | Higher complexity → slower |
| `n_calls` | +0.74 | More function calls → slower |
| `n_greater` | +0.71 | More `greater()` ops → slower |
| `n_constants` | +0.71 | More fitted constants → slower |
| `frac_const_leaves` | +0.71 | Constant-heavy leaves → slower |
| `frac_var_leaves` | −0.71 | Variable-heavy leaves → faster |
| `frac_internal_w_vars` | −0.71 | Internal nodes touching variables → faster |
| `const_mean_abs` | −0.70 | Larger constant magnitudes → faster |
| `x_depth_std` | −0.69 | Uneven x depths → faster |

The dominant signal on CPU is **raw tree size**: more nodes, more work, more time. This is different from GPU, where depth and variable placement mattered more than node count. On CPU the compiler sees the full scalar expression and can reorder/CSE aggressively — what you can't compress away is the total number of distinct operations. `greater()` shows up strongly because each one becomes a compare+conditional-move on x86, which while branchless still costs a cycle and occupies a register.

The speed-positive features tell a consistent story: equations where internal nodes are doing real variable computation (not just shuffling constants) tend to be shorter after constant folding, which is where the runtime actually goes.

## GPU Results

| Metric | Value |
|--------|-------|
| Unique equations benchmarked | 8,256 |
| Minimum MAE achieved | 0.000949 |
| Equations within 30% of min loss | 240 |
| Baseline (2× `__expf`, `--use_fast_math`) | 24.34 G-ups/s |
| Best SR throughput (within accuracy tier) | 24.53 G-ups/s |
| Throughput range (top accuracy tier) | 23.4 – 24.5 G-ups/s |

The approximations cluster tightly around the baseline. The best accurate equation barely edges it out (~+0.8%) but nothing achieves a dramatic speedup.

This is not a failure of the search — it's the ceiling of the problem. With `--use_fast_math`, NVIDIA's `__expf` is a ~4-cycle hardware instruction that the SM can overlap with other work. The softmax kernel is latency-bound on the sequential dependency chain through `m` and `s`, not compute-bound on `exp`. Replacing `exp` with cheaper arithmetic saves a few instructions but doesn't widen the critical path or change the memory access pattern. The bottleneck is the serial recurrence, not the arithmetic inside it.

More concretely: the kernel has one thread per sequence, so there is no intra-sequence parallelism to exploit. Every step depends on the previous `m` and `s`. Whether that step costs one `__expf` or three multiplications, the compiler still has to retire them serially. The GPU's ability to hide latency through warp switching is limited by the small number of registers each thread is touching — it's already hiding most of what it can.

A warp-reduction kernel (where a warp cooperatively processes one sequence) would change which equation structures are fastest, but that's a different kernel shape entirely.

## Structural Predictors of GPU Throughput

At the 30% loss threshold, features most correlated with throughput across 240 equations:

| Feature | r | Direction |
|---------|---|-----------|
| `n_constants` | −0.62 | More fitted constants → slower |
| `x_min_depth` | −0.59 | `x` buried deep in tree → slower |
| `frac_const_leaves` | −0.56 | Constant-heavy leaves → slower |
| `frac_var_leaves` | +0.56 | Variable-heavy leaves → faster |
| `all_var_depth_mean` | −0.53 | Deep variables on average → slower |
| `n_mx_products` | −0.48 | `m×x` interactions → slower |
| `x_poly_degree` | +0.40 | Higher x polynomial degree → faster |
| `n_const_mul` | +0.37 | Foldable constant products → faster |

The clearest story: variable depth is the dominant structural predictor. Deep `x` occurrences create serial dependency chains that can't be pipelined. Constant-heavy expressions (finely fitted polynomial approximations) have high leaf count without proportional arithmetic benefit. Expressions built around `x²` fare better — they replace `exp` with a multiply while still capturing the local curvature.

## Speed-Aware SR Loss

These correlations were fed back into the search as a structural penalty:

```
loss = MAE + SPEED_WEIGHT × speed_score
SPEED_WEIGHT = 2e-4
```

The speed score (∈ [0, 1]) penalises average `x` depth (w=0.28), variable depth variance (w=0.20), fraction of constant leaves (w=0.30), and op-type diversity (w=0.14), and rewards `x²` patterns (w=−0.08). At typical MAE ~0.003, the maximum penalty is ~0.0002 — enough to break ties between equally accurate equations toward structurally faster forms, without steering the search away from good solutions early.

## Usage

```
# Run symbolic regression
julia run_sr.jl                  # flat depth penalty
julia run_sr_tree_loss.jl        # data-driven structural penalty

# CPU benchmarks (reads from equation_features.csv by default)
python eval_cpu_bench.py
python analyze_cpu_bench.py --threshold 0.30 --top 20

# CPU benchmarks from a specific hall-of-fame CSV
python eval_cpu_bench.py --source outputs/<run>/hall_of_fame.csv --col Equation

# GPU benchmarks from a run directory
just cuda-direct <dir>
cd <dir> && make bench

# Full GPU eval across all run directories
just run-cuda-eval

# GPU feature analysis on bench_results.csv
python analyze_bench.py --threshold 0.30 --top 40
```
